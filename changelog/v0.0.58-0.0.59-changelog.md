# v0.0.58 -> v0.0.59

People whose numbers were scraped from someone else's public listing can now
take themselves off Drop.

## Removing your own listing

Imported listings became callable in 0.0.53, but the only route off the
directory was *claiming* the profile — which meant creating an account in order
to leave. That was backwards, and this closes it.

- New `/directory/remove`: enter your number, confirm the code, and every
  listing carrying that number comes off. **No account, no password.**
- Control of the number is proved by SMS, so nobody can remove your listing and
  nobody can remove someone else's.
- The request step answers identically whether or not the number is listed, so
  the page cannot be used to test which numbers are in the directory.
- Linked from the imported archive and the privacy policy, and in the sitemap,
  so someone looking for it can find it without asking us.

## A removal stays removed

- The row is marked withdrawn rather than deleted. Deleting would leave no
  evidence the request was honoured, and would let the next scrape restore the
  person.
- `scripts/import-donors.ts` now carries withdrawals forward, so re-importing
  the same source does not undo them. The source still publishes those people;
  we still do not. Verified by re-importing a withdrawn record and confirming it
  stayed off search, the detail page, and the reveal.
- Every read path excludes withdrawn listings by default. A caller has to ask
  for them explicitly, so a future query cannot expose them by forgetting to
  exclude them.

## Faster schema migrations

- The imported-donor backfill rewrites rows in passes, and each pass re-scans
  the table — so the number of passes, not the number of rows, is the cost.
  Raising the batch from 1,000 to 10,000 cuts a 129k-row migration from about
  130 passes to 13, and from roughly forty minutes to a few. It costs
  10-20 MB of peak boot memory.
- Adding `listing_state` needed no migration pass at all: every existing row is
  correctly active, so the column default is the whole migration.

## Also

- `POST /api/auth/otp/request` and the removal flow now share one challenge
  issuer, instead of the send/cooldown/rollback logic existing twice.
